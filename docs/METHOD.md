# 执行方法 V5 · 公开方法版1.0

## 目标和判断标准

先固定质量、安全、正确性、约定成本、成功率、资源及授权边界，再优化完整有效交付时间：`T* = min(T_VALID_E2E)`。

计时从收到可执行合同至合格成品和交付回执读回，包含检索、配置、等待、模型、执行、验收、失败、返工、恢复及交付。首次建设、冷安装、热复用分别记录；局部脚本耗时不能代替整个工程耗时。未验收为 `NOT_VALID（未合格）`，没有完整计时为 `NOT_MEASURED（未测量）`。保护性拒绝、停止对账也不能算成成功交付。

更短时间是相同标准下的效率指标；收入和净利润还取决于需求、价格、成交、收款及完整成本，必须分别记录。

## 1. 明确真实合同

采用[任务模板](../templates/TASK.md)。先把模糊愿望变成输入、成品、验收、时限、预算、权限和故障边界。信息充分就做，不因例行确认中断已授权工作。影响结果的缺失信息必须标明，不把假设写成已知事实。

重大、难逆或高不确定决策，简要完成：定义问题→核实关键事实→比较可行路线与最强反例→决定执行、暂缓、观察、仅参考或停止。简单任务不增加流程负担。

## 2. 复用成熟路径

先查现有经验索引及命中的少量卡片，再找成熟产品、模板、合法可复用源码、官方接口或现有完整脚本。经验必须匹配当前合同、环境与版本；以最新原始回执判断状态，不把旧通过当成现在健康。

候选最多三条，简单任务一条即可。比较完整接入、运行、审核、恢复时间和总成本；接入复杂的新框架不天然胜过已有脚本。没有会改变选择的新事实就停止搜索。

能用确定性工具完成时不必调用模型。专业执行器或并行只有在降低同质量完整交付时间时才加入；同一业务实例只允许一个控制者。使用第三方资产遵守原许可，不因本项目开源就视为第三方资产可任意再发布。

## 3. 虚拟成熟与冻结

依据真实文档、代码、经验和已知输入检查完整路径：输入→执行→产物→验收→提交→回执；再检查缺依赖、格式歧义、权限、重复遗漏、进程退出、部分写入、未知提交及恢复。

明确验收、必需依赖、可行最短路径和主要异常处理后，冻结合同、配方/配置身份及验收办法。推演不是现实通过，也不是性能证明。不要无限追求理论最优；继续比较的预期收益不足以覆盖耗时就进入现实执行。

## 4. 一次整体现实执行

执行已冻结路径，记录真实阶段结果。进程受理、文件保存、退出码0、模型自报完成都不能替代成品验收。

普通故障最小修复后继续原任务，保留失败记录。确需改变路线时注明依据，更新受影响冻结内容；不暗改成功标准。已经确认完成的步骤继承，不因换页、换模型或改名字重新执行。

## 5. 主备独立与交接

正常由选定一端独立推进，不要求另一端在线，也不在交付后互相重启。确需持续运行时接入已有成熟持久执行器，不另造调度、记忆或锁服务。

发生故障后：

1. 保留原任务号、输入位置与哈希、检查点、已有产物及提交回执。
2. 确认旧执行进程/执行树已停止，核清已发生的外部动作，再取得已有锁或执行权。
3. 按[接续模板](../templates/HANDOFF.md)移交最小信息；备用只完成剩余工作。
4. 优先继承已确认成品。可用成熟确定性配方恢复时先用配方，必要时才调用备用模型。
5. 对 `UNKNOWN（状态未知）` 先只读对账；只有确认未执行才重试。部分产物、锁或进程不明时安全停止并保留证据，不能换入口盲发。

共享同一机器的主备仍共享操作系统、磁盘等风险；不能称为异机容灾。人工接手属于人工介入；一次零介入不能证明长期稳定。无人值守超时恢复、外部付款/邮件恰好一次等须单独验证。

## 6. 独立验收与交付

用原始输入、确定性检查或适用的独立审核检查完整性、一致性、业务正确性和约定成品质量。生成模型自评不能作为唯一验收依据。对账、权限和质量检查属于交付时间的一部分。

交付成品、验收范围、完整用时、每份合格交付成本、人工介入次数、故障恢复证据。账单缺失就记未知；模型任务数不等同于API请求数。

只将有来源、会改变行动的经验写回已有知识入口，记录触发条件、根因、修正、真实结果及不适用条件。方法改了、文档保存了、技能能被找到，都不等于业务质量或效率已经提高。
